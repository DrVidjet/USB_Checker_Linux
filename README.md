# Монитор USB и поиск драйверов на ОС Linux

Модуль `usbmon` отслеживает подключение устройств USB, показывает полное
наименование устройства и проверяет, есть ли для него драйвер в ядре Linux.
Модуль `drvsearch` ищет внешний драйвер на GitHub с помощью локальной языковой
модели и выдаёт ссылки и шаги установки, взятые только из README найденных
репозиториев. Окно поиска открывается кнопкой «Найти драйвер» (Ctrl+F) и
работает как отдельный процесс, связанный с главным окном двумя каналами (pipe).
Кнопка «Найти драйвер без ИИ» (Ctrl+Shift+F) открывает такое же окно, но поиск
идёт только по GitHub и README, без языковой модели: быстрее и не занимает
память, даже если модель готова.
Языковую модель программа готовит сама: при запуске проверяет мощность
компьютера, скачивает Ollama и модель `qwen2.5:1.5b` в папку `model` проекта и
один раз проверяет модель на задачах программы (раздел «Языковая модель»).

## Установка

Программа работает в любом дистрибутиве Linux на x86_64 с glibc и Python 3.10
или новее. Python-зависимости ставятся через pip в виртуальное окружение
проекта, системные пакеты - только те, что не относятся к Python.

1. Системные пакеты: Python с модулем `venv` и база названий устройств
   `usb.ids` (без неё модуль тоже работает, но берёт названия только из строк
   самого устройства).

   | Дистрибутив | Команда | Где окажется usb.ids |
   |---|---|---|
   | Arch, Manjaro | `sudo pacman -S --needed python hwdata` | `/usr/share/hwdata/usb.ids` |
   | Debian 12+, Ubuntu 24.04 | `sudo apt install python3-venv usb.ids` | `/usr/share/misc/usb.ids` |
   | Fedora | `sudo dnf install python3 hwdata` | `/usr/share/hwdata/usb.ids` |

   В Debian и Ubuntu модуль `venv` вынесен в отдельный пакет `python3-venv`,
   без него `python3 -m venv` не создаст окружение. В Arch и Fedora он входит
   в пакет Python. В других дистрибутивах нужен Python 3.10+ с `venv`;
   файл `usb.ids` программа ищет и в `/usr/share/usb.ids`,
   `/var/lib/usbutils/usb.ids`.

2. Виртуальное окружение и зависимости (из корня проекта):

   ```
   python3 -m venv .venv
   .venv/bin/pip install -r requirements.txt
   ```

   `requirements.txt` закрепляет версии PyQt5 5.15.11, PyQt5-Qt5 5.15.19 и
   PyQt5-sip 12.20.0. Они ставятся готовыми колёсами (manylinux, x86_64)
   вместе с библиотекой Qt 5.15, компилировать ничего не нужно. Нужен
   Python 3.10 или новее (так требует PyQt5-sip 12.20.0). Для Python 3.10-3.13
   ставится ещё `zstandard` 0.25.0 - им распаковывается архив Ollama; в
   Python 3.14 для этого есть стандартный модуль `compression.zstd`.

   Колёса PyQt5-Qt5 на PyPI выпускаются только для x86_64. На ARM64
   (Raspberry Pi и т.п.) окно через pip не установится, но консольные режимы
   и подготовка модели работают и без PyQt5.

3. Запуск интерпретатором окружения:

   ```
   .venv/bin/python run_usb_monitor.py
   ```

   При первом запуске окно сразу работает, а в строке состояния справа
   видна подготовка модели: проверка, загрузка с процентами, «Модель
   qwen2.5:1.5b готова». Подробности - в разделе «Языковая модель».

   Или активируйте окружение, и тогда команды `python` и `pip` будут
   указывать на него: `source .venv/bin/activate` для bash и zsh,
   `source .venv/bin/activate.fish` для fish, выход - `deactivate`.

Окно поиска драйвера запускается тем же интерпретатором, что и главное окно
(`sys.executable`), поэтому тоже работает из окружения.

Каталог `.venv` не переносится на другой компьютер: в его скриптах записаны
абсолютные пути. Поэтому в архив проекта для проверки кладётся
`requirements.txt`, а окружение создаётся заново командами из шага 2
(`.venv` указан в `.gitignore`).

Права root не нужны: события ядра через netlink может получать любой
пользователь, а Ollama и модель лежат в папке проекта.

### Если установка или запуск не удались

**`error: externally-managed-environment` при `pip install`.** Команда `pip`
без активации окружения относится к системному Python, а Arch запрещает
ставить в него пакеты через pip (PEP 668). Используйте pip окружения:
`.venv/bin/pip install -r requirements.txt` или сначала
`source .venv/bin/activate`.

**`Could not find the Qt platform plugin "xcb" in ""`** (или `"wayland"`).
Qt не нашёл каталог своих плагинов. Причина - ошибка PyQt5: путь к своей копии
Qt он передаёт в кодировке Latin-1, и кириллица в пути к проекту
(например, `~/Документы/Курсовая`) превращается в «?». Программа обходит это
сама (модуль `qtenv.py` передаёт Qt правильный путь через переменные
`QT_QPA_PLATFORM_PLUGIN_PATH` и `QT_PLUGIN_PATH`). Если ошибка всё же
появилась, пришлите вывод команды
`QT_DEBUG_PLUGINS=1 .venv/bin/python run_usb_monitor.py`.

**`Could not load the Qt platform plugin "xcb" ... even though it was found`.**
Плагин найден, но в системе нет нужных ему библиотек X11 (на полноценном
рабочем столе они обычно уже установлены). Чего не хватает, покажет запуск с
`QT_DEBUG_PLUGINS=1`. В Arch чаще всего это:

```
sudo pacman -S --needed xcb-util-wm xcb-util-image xcb-util-keysyms xcb-util-renderutil libxkbcommon-x11
```

**«Модель недоступна» или «ИИ отключён» в строке состояния.** Откройте
«Модель → Сведения о модели → Показать подробности...»: там по шагам записано, что
программа проверила и чем закончился каждый шаг (мощность компьютера,
загрузка, служба, самопроверка модели). Тот же отчёт печатает команда
`.venv/bin/python -m drvsearch --setup-model`. После устранения причины
выберите «Модель → Повторить подготовку и проверку»; загрузка продолжится с
того места, где прервалась. Вывод службы Ollama записан в
`model/ollama-serve.log`.

**Модель скачивается заново.** Программа ищет модель только в папке
`model/models` той копии проекта, из которой запущена (в журнале будет строка
«модели … нет в <каталог>, она будет скачана»). Если новая версия программы
распакована в другую папку, перенесите в неё папку `model` из старой копии -
тогда ни Ollama, ни модель скачивать не придётся.

**«нет связи с реестром моделей Ollama» или «служба Ollama больше 120 с не
получает данных от реестра моделей».** Модель скачивается с
`registry.ollama.ai`, а её файлы - с сервера хранения, на который реестр
перенаправляет запрос. Сама Ollama ждёт ответа этих серверов без ограничения
времени, поэтому перед загрузкой программа проверяет связь с ними сама (до
30 с на запрос) и пишет причину: не найден адрес (DNS), соединение отклонено
или сброшено, ошибка TLS, сервер не ответил. Если ollama.com открывается у вас
только через VPN или прокси, включите его перед загрузкой: служба Ollama
получает от программы все переменные окружения, в том числе настройки прокси.

## Языковая модель

Модель нужна только для поиска драйверов. Без неё поиск тоже работает:
ключевые слова берутся регулярным выражением, кандидаты оцениваются по
признакам, шаги установки - блоки кода из README. Модель улучшает выбор
ключевых слов, оценку кандидатов и пересказ шагов.

### Какая модель и почему

По умолчанию - **`qwen2.5:1.5b`** (файл 986 МБ, лицензия Apache 2.0).
Задачи у модели узкие: выделить обозначение микросхемы, оценить, подходит ли
репозиторий, переписать команды из README. Ответ всегда - JSON по схеме
(параметр `format` в Ollama), поэтому формат ответа соблюдается у любой
модели, а от самой модели нужно точно следовать инструкции. Выбор:

| Модель | Файл | Нужно памяти* | Вывод |
|---|---|---|---|
| `qwen2.5:0.5b` | 398 МБ | 1,0 ГБ | слишком слаба: IFEval 27,9 (следование инструкциям) |
| **`qwen2.5:1.5b`** | 986 МБ | 1,6 ГБ | IFEval 42,5; в карточке модели прямо названа генерация JSON; всего 2 головы KV - маленький кэш |
| `qwen3:0.6b` | 523 МБ | 1,9 ГБ | 8 голов KV: кэш на 8192 токена больше самой модели |
| `qwen3:1.7b` | 1,4 ГБ | 2,7 ГБ | почти вдвое больше памяти при той же задаче |
| `qwen2.5:3b` | 1,9 ГБ | 2,6 ГБ | точнее, можно выбрать параметром `--model qwen2.5:3b` |

\* файл модели + кэш внимания на 8192 токена + 0,5 ГБ на службу Ollama
(расчёт ниже). Цифры IFEval (strict-prompt) - из блога Qwen2.5.

**Язык ответов.** Системный промт, задания и описания полей JSON-схемы
написаны по-английски, и пояснения модели (почему репозиторий подходит, что
делает шаг установки) тоже английские; остальной интерфейс программы русский.
Сначала пробовали получать пояснения по-русски (русские промты и проверка
языка ответа), но на настоящих `qwen2.5:1.5b` и `qwen2.5:3b` ответы не
проходили проверку языка, и самопроверка отключала модель. Язык ответов
больше не проверяется. Названия репозиториев, микросхем и команды модель не
меняет.

Контекст 8192 токена взят с запасом: самый длинный запрос программы (оценка
шести кандидатов с отрывками README) - около 6 000 символов, то есть 2-2,5
тысячи токенов, плюс до 900 токенов ответа. Обрезки запроса не бывает.

**Самопроверка.** Модели в среде разработки запустить было нельзя, поэтому
проверку на наших задачах делает сама программа на вашем компьютере. Сразу
после загрузки модель решает три задания с заранее известным ответом - теми
же запросами и схемами, что при поиске (`drvsearch/selftest.py`):

1. выделить `rtl8188eus` из названия «Realtek ... RTL8188EUS 802.11n
   Wireless Network Adapter»;
2. из двух репозиториев признать драйвером нужный (он стоит вторым), дать
   ему оценку выше, чем постороннему «awesome»-списку;
3. переписать команды установки из фрагмента README дословно (`make` и
   `sudo make install` должны быть, выдуманных команд - не больше одной).

На каждое задание даётся 90 секунд, первое включает загрузку модели в
память. Если модель ошиблась или не уложилась, программа её не использует:
в строке состояния будет «ИИ отключён: модель не прошла проверку», поиск
идёт без модели, а программа подскажет модель крупнее (`--model
qwen2.5:3b`), если дело не в скорости. Результат сохраняется в
`model/selftest.json` вместе с
отпечатком модели и номером версии заданий, поэтому проверка проходит один
раз (после смены заданий - ещё раз, автоматически); заново - «Модель →
Повторить подготовку и проверку» или `--setup-model --retest`.

### Системные требования

Модель считается на процессоре и целиком лежит в оперативной памяти.
Видеокарта не нужна.

| | Минимум (проверяет программа) | Рекомендуется |
|---|---|---|
| ОЗУ всего (`qwen2.5:1.5b`) | 3,1 ГБ | 4 ГБ и больше |
| Свободной ОЗУ перед поиском | 1,6 ГБ | 2 ГБ |
| Процессор | x86_64 с AVX или ARM64, 2 потока | AVX2, 4 потока |
| Диск | архив Ollama 1,34 ГБ + распакованные файлы + модель 1 ГБ | 5 ГБ свободно |
| Сеть | только для первой загрузки | |

Для `--model qwen2.5:3b`: ОЗУ всего от 4,1 ГБ, свободной перед поиском 2,6 ГБ.

По документации Ollama (troubleshooting) быстрее всего она работает с AVX2,
медленнее - с AVX, а без AVX использует самый медленный вариант; такой
процессор программа считает слишком слабым.

Как считается память (`drvsearch/hwcheck.py`): файл модели + кэш внимания на
8192 токена (2 × слои × головы KV × размер головы × 2 байта - тип кэша `f16`,
он у Ollama по умолчанию) + 512 МБ на буферы и саму службу. Для
`qwen2.5:1.5b` это 28 слоёв, 2 головы KV по 128 (файл `config.json` модели),
то есть 0,92 ГБ + 0,22 ГБ + 0,5 ГБ = 1,6 ГБ. У скачанной модели параметры
берутся из ответа Ollama `/api/show`, так что расчёт работает и для других
моделей. К «ОЗУ всего» прибавлено 1,5 ГБ на систему и рабочий стол.

**Защита от слабого компьютера:**

1. Перед загрузкой проверяются процессор (число потоков, AVX) и объём ОЗУ.
   Если компьютер слишком слабый, программа ничего не скачивает, в строке
   состояния пишет «ИИ отключён: слабый компьютер», а поиск идёт без модели.
2. Самопроверка (см. выше) отсеивает компьютер, на котором модель отвечает
   слишком медленно.
3. Перед каждым поиском проверяется свободная сейчас память (`MemAvailable`
   из `/proc/meminfo`). Если её мало, этот поиск идёт без модели, а в отчёте
   написано, сколько памяти освободить. Если модель уже загружена в память
   Ollama (`/api/ps`), свободная память для неё не нужна.
4. Если ответ модели во время поиска занял больше 120 секунд или Ollama
   ответила ошибкой (например, «model requires more system memory»),
   остальные вопросы в этом поиске модели не задаются.

Отключить проверку мощности: `SUPERAPP_IGNORE_HW=1 .venv/bin/python run_usb_monitor.py`.

### Подготовка при запуске

Ollama - отдельная программа, а не Python-пакет, поэтому через pip она не
ставится. Её и модель программа (`drvsearch/runtime.py`) в фоновом потоке
главного окна всегда скачивает в папку `model` в корне проекта. В систему
ничего не ставится, права root не нужны; Ollama, установленная в системе,
и её служба не используются.

1. **Мощность компьютера** (см. выше). Слабый компьютер - дальше не идём.
2. **Ollama** - программа, которая запускает модель. Если в `model/ollama`
   её нет, программа скачивает переносимую сборку с ollama.com
   (`ollama-linux-amd64.tar.zst` или `ollama-linux-arm64.tar.zst` - тот же
   архив, что в разделе «Manual install» документации Ollama для Linux) и
   распаковывает её туда. `.tar.zst` - это обычный tar-архив, сжатый
   алгоритмом Zstandard (как `.tar.gz`, только другим сжатием), а не пакет
   дистрибутива: он одинаковый для всех Linux, распаковывается модулем
   `tarfile` из Python, пакетный менеджер в этом не участвует. Пакеты Arch
   тоже сжимаются zstd, но называются `*.pkg.tar.zst` и ставятся через pacman.
3. **Служба.** Программа запускает `ollama serve` на `127.0.0.1:11435`
   (переменные `OLLAMA_HOST` и `OLLAMA_MODELS`), модели хранятся в
   `model/models`. Если служба осталась от прошлого запуска (например, после
   сбоя), используется она.
4. **Модель.** Если её нет в списке `GET /api/tags`, программа скачивает её
   запросом `POST /api/pull` и показывает проценты.
5. **Самопроверка модели** (один раз).

Что лежит в папке `model` (она в `.gitignore`):

```
model/
  ollama/                 переносимая сборка Ollama (bin/ollama, lib/ollama)
  models/                 модели
  selftest.json           результат самопроверки модели
  *.tar.zst.part          недокачанный архив (докачивается при следующем запуске)
  ollama-serve.log        вывод службы Ollama
```

Когда модель готова, главное окно сообщает адрес службы окнам поиска по
каналу (сообщение `model`): окно, открытое во время загрузки, ищет без модели,
а после сообщения подсказывает нажать «Повторить поиск». Если модель
отключена, окно поиска получает сообщение об этом и ищет без неё.

Службу программа останавливает при закрытии окна (запуск и завершение
процесса `ollama serve` записываются в лог-файл).

### Сколько скачивается

| Что | Размер | Примерно при 250 КБ/с |
|---|---|---|
| Ollama для x86_64 (v0.35.1) | 1,34 ГБ | 1,5 ч |
| Модель `qwen2.5:1.5b` | 986 МБ | 1,1 ч |

Архив Ollama большой, потому что содержит библиотеки для видеокарт NVIDIA;
скачивается он один раз.

### Загрузка прерывается и продолжается

* Закрыть окно можно в любой момент. Недокачанный архив хранится как
  `model/*.tar.zst.part` и при следующем запуске докачивается запросом с
  заголовком `Range`; прерванный `/api/pull` по документации Ollama тоже
  продолжается с места остановки.
* Меню «Модель»: «Сведения о модели» (мощность компьютера, самопроверка,
  отчёт о шагах), «Остановить загрузку», «Повторить подготовку и проверку».
* Перед загрузкой проверяется свободное место (архив плюс распакованные
  файлы, модель плюс 10 %).

### Параметры

```
.venv/bin/python run_usb_monitor.py --model qwen2.5:3b   # модель точнее, но больше
.venv/bin/python run_usb_monitor.py --no-model           # не проверять и не скачивать
.venv/bin/python -m drvsearch --setup-model              # подготовить модель в консоли
.venv/bin/python -m drvsearch --setup-model --retest     # и проверить её заново
```

`--setup-model` делает то же, что главное окно, показывает проценты в
терминале и в конце печатает отчёт; Ctrl+C прерывает загрузку, повторный
запуск её продолжает. Консольный поиск (`-m drvsearch --vid ... --pid ...`)
модель не скачивает: он использует уже скачанную и проверенную модель из
папки `model`.

Переменные окружения:

| Переменная | Что меняет |
|---|---|
| `SUPERAPP_LLM_MODEL` | модель вместо `qwen2.5:1.5b` |
| `SUPERAPP_OLLAMA_PORT` | порт службы вместо 11435 |
| `SUPERAPP_MODEL_DIR` | папка вместо `model` в корне проекта |
| `SUPERAPP_IGNORE_HW=1` | не проверять мощность компьютера |
| `SUPERAPP_OLLAMA_DOWNLOAD` | адрес загрузки вместо `https://ollama.com/download` |

Удалить всё, что скачала программа: удалить папку `model` в корне проекта.

### Ограничения

* Переносимая сборка Ollama выпускается только для x86_64 и ARM64; на других
  архитектурах программа сообщает об этом, и поиск работает без модели.
* Дополнительный архив ROCm для видеокарт AMD программа не скачивает.

### Токен GitHub (необязательно)

Без токена GitHub разрешает 10 поисковых запросов в минуту и 60 запросов в час,
одного поиска (до 4 запросов поиска и до 6 чтений README) хватает. С токеном лимит
выше и включается поиск по коду: программа находит репозитории, в исходниках
которых есть таблица устройств с нужной парой VID:PID. Токену достаточно доступа
только на чтение публичных репозиториев. Его можно передать переменной
`GITHUB_TOKEN`.

## Запуск

Команды выполняются из корня проекта; при активированном окружении вместо
`.venv/bin/python` можно писать просто `python`.

```
.venv/bin/python run_usb_monitor.py                         # окно
.venv/bin/python -m usbmon                                  # консоль: список и слежение
.venv/bin/python -m usbmon --list                           # консоль: только список
.venv/bin/python -m usbmon --json                           # консоль: вывод в JSON
.venv/bin/python -m drvsearch --vid 0bda --pid 8179         # поиск драйвера в консоли
.venv/bin/python -m drvsearch --vid 0bda --pid 8179 --no-llm  # без языковой модели
.venv/bin/python -m drvsearch --window --vid 0bda --pid 8179  # окно поиска отдельно
.venv/bin/python -m drvsearch --setup-model                 # проверить и скачать модель
.venv/bin/python -m unittest discover -s tests -v           # тесты
```

Консольные режимы `usbmon` и `drvsearch` используют только стандартную
библиотеку (и `zstandard` для распаковки Ollama на Python до 3.14) и работают
даже без установленного PyQt5.

Лог-файл пишется в `logs/usb_monitor.log` (путь меняется параметром `--log`).

## Как это работает

1. **Слежение.** Сокет `AF_NETLINK` семейства `NETLINK_KOBJECT_UEVENT`
   подписан на группу 1, куда ядро рассылает события `add`, `remove`, `bind`,
   `unbind` и т.д. (`lib/kobject_uevent.c`). В окне дескриптор сокета подключён
   к циклу событий Qt через `QSocketNotifier`, в консоли через `poll(2)`.
   Если сокет открыть не удалось, включается опрос sysfs раз в 2 секунды.
2. **Задержка проверки.** После `add` ядро ещё создаёт интерфейсы, а udev
   загружает модули. Поэтому устройство проверяется через 0,8 с после
   последнего события по нему.
3. **Наименование.** Строки `manufacturer` и `product` из
   `/sys/bus/usb/devices/<порт>/`; если их нет, используется название
   из `usb.ids` по паре VID:PID. Показываются оба варианта.
4. **Проверка драйвера** для каждого интерфейса:
   * есть ссылка `driver`: драйвер работает; по ссылке `driver/module` и
     файлу `/sys/module/<модуль>/initstate` определяется, встроен он в ядро
     или загружен модулем;
   * драйвер `usbfs`: интерфейс занят программой через libusb;
   * ссылки нет: `modalias` интерфейса сравнивается (как в modprobe, через
     `fnmatch`) с шаблонами из `/lib/modules/$(uname -r)/modules.alias` и
     `modules.builtin.modinfo`; учитываются записи `blacklist` из каталогов
     modprobe.d и параметр ядра `modprobe.blacklist=`;
   * для классов, которые обслуживают программы пользователя (PTP/MTP,
     смарт-карты, DFU), отсутствие драйвера ядра не считается проблемой.

Итог по устройству: «работает», «не требуется», «не работает» (модуль есть,
но не загружен, в чёрном списке или не привязался), «не найден» (здесь
потом подключится поиск внешнего драйвера) или «заблокировано»
(`authorized = 0`, например USBGuard).

## Как работает поиск драйвера

1. **Ключевые слова.** Обозначения микросхем (RTL8188EUS, MT7921U, AX88179)
   выделяются из названий регулярным выражением; модель может добавить свои,
   они проходят фильтр (только `[a-z0-9._-]`, без общих слов вроде «usb»).
2. **Поиск на GitHub.** `GET /search/repositories` по запросам вида
   `rtl8188eus linux driver` и `0bda 8179 in:readme`; с токеном также
   `GET /search/code` по запросу `0x0bda 0x8179 language:C`.
3. **Оценка.** Признаки: совпадение названия с микросхемой, упоминание VID:PID
   в описании и README (`GET /repos/{owner}/{repo}/readme`), таблица устройств
   в коде, звёзды, дата последнего изменения, архивность, форк. Модель
   (Ollama, `POST /api/chat` с JSON-схемой в `format`, температура 0)
   оценивает до 6 кандидатов. Кандидаты без единого совпадения отсеиваются.
4. **Шаги установки** - только из README: модель пересказывает раздел
   об установке, но каждая её команда проверяется на дословное наличие в README;
   выдуманные команды отбрасываются. Без модели показываются блоки кода
   из раздела «Installation».
5. **Предупреждения:** архив, давно не обновлялся, мало звёзд, нет лицензии,
   форк, опасные команды (`curl ... | sh`, `dd if=`, `mkfs`, `rm -rf /`).
   Программа ничего не устанавливает и не выполняет.
6. **Ссылки** берутся только из ответов GitHub API: модель ссылается на
   кандидатов по номеру и не может добавить свою ссылку.
7. **Кэш.** Последний результат по каждому VID:PID хранится в
   `~/.cache/superapp/drvsearch/`; если GitHub недоступен (нет сети, лимит),
   показывается он - это страховка для защиты.

### Окно поиска - отдельный процесс (вариант задания: каналы)

Главное окно создаёт два канала `pipe(2)` и запускает
`python3 -m drvsearch --window --in-fd R --out-fd W` через `fork`/`execve`
(`subprocess.Popen` с `pass_fds`). По каналу «главное окно -> окно» идут
сведения об устройстве, по каналу «окно -> главное окно» - ход поиска и
результат; формат - JSON Lines. Главное окно записывает запуск, результат и
завершение процесса в лог-файл. Когда главное окно закрывается, его концы
каналов закрываются, окно поиска получает конец файла и завершается само.
Реестр порождённых процессов (`PopupManager.processes`) пригодится монитору
процессов.

## Системные вызовы (для отчёта)

| Вызов | Где используется |
|---|---|
| `socket(2)`, `bind(2)`, `recvfrom(2)`, `setsockopt(2)` | приём событий ядра, `usbmon/uevent.py` |
| `poll(2)` | ожидание событий в консольном режиме, `usbmon/__main__.py` |
| `open(2)`, `read(2)`, `close(2)` | чтение атрибутов sysfs и файлов модулей, `usbmon/sysio.py` |
| `readlink(2)` | ссылки `driver` и `module`, `usbmon/sysio.py` |
| `getdents64(2)` (через `os.listdir`) | перечисление устройств и интерфейсов |
| `access(2)` | проверка наличия файлов |
| `open(2)` с `O_APPEND`, `write(2)` | лог-файл, `usbmon/tracker.py` |
| `uname(2)` | версия работающего ядра |
| `pipe(2)`, `fork(2)`/`execve(2)`, `wait4(2)` | окно поиска как отдельный процесс, `usbmon/popups.py` |
| `read(2)`, `write(2)` по каналам | обмен JSON Lines, `drvsearch/channel.py` |
| `fork(2)`/`execve(2)`, `kill(2)` (SIGTERM, SIGKILL), `wait4(2)` | запуск и остановка `ollama serve`, `drvsearch/runtime.py` |
| `statfs(2)` (через `shutil.disk_usage`) | проверка свободного места перед загрузкой |
| `rename(2)` (через `os.replace`) | готовый файл появляется только после полной загрузки или распаковки |
| `shutdown(2)` | прерывание загрузки из другого потока при закрытии окна |
| `connect(2)`, `recv(2)` (через `urllib`) | загрузка Ollama и модели, запросы к Ollama и GitHub |
| `sched_getaffinity(2)`, чтение `/proc/meminfo` и `/proc/cpuinfo` | проверка мощности компьютера, `drvsearch/hwcheck.py` |
